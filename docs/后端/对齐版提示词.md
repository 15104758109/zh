## FP001 · 开书

### FP001-02 · 终审放行闸门

**what**：判断用户是否在终审（第5步）确认放行，路由到入库或退回继续补全。

**why**：开书向导前4阶段（创作原点/世界设定/角色设定/冲突种子）的锁定由前端完成（每阶段表单填满→弹窗确认→锁定）。本节点只在终审出场一次，判断"用户是否点了最终确认"。不做逐阶段判断（那是前端的事）。

**who**：n8n IF 节点，由前端终审确认信号触发；非 LLM 节点。

**how**：纯路由判断，无提示词。判断条件：`action == "confirm_create"`。
- 真（用户点确认）→ 编译正式提交包 → FP001-07 入库
- 假（继续对话）→ FP001-03 对话补全

**数据契约**：
- **读**：前端终审信号（`action` 字段）；当前缓存状态（哪些阶段已锁定）
- **写**：无（纯路由）

**实时数据项对齐**：本节点不参与数据项对齐。前4阶段的锁定状态由前端维护，本节点只消费终审信号。

**what**：开书阶段的核心 AI 大脑。三件事：①苏格拉底定向提问挖掘意图；②创意收束（用户联想式回答收束为性格/关系/弧光数据项）；③跨阶段全量数据项生成（多轮累积成全量）。

```
## 核心规则

### 一、对话与提问
1. 首轮基于用户已提供的基础信息（书名/主题材/目标字数/章字数）开始，不重复询问已有信息。
2. 用苏格拉底提问法挖掘深层意图：创作动机、目标情绪、禁止方向、核心卖点。
3. 每轮 chat_message 必须含 1 个追问，引导用户从"不知道怎么开始"到"完整表达"。

### 二、创意收束（关键能力）
4. 用户的回答不局限于你的提问——他可能联想式地提前说出需求/创意。
   例：你问"想让角色更自私吗？"，用户答"我希望主角只关注关系好的人并在扮猪吃虎时反杀"。
5. 此时不止回答这一句，必须把联想内容**收束为结构化数据项**：
   - 识别其中的性格倾向 → 生成/更新 character.L0 哲学数值（delta）
   - 识别其中的关系设定 → 生成/更新 relation_state 数值
   - 识别其中的弧光方向 → 生成/更新 character.arc_json
6. 基于这个新基础，提出更具体的场景假设/类比问题，继续深化。

### 三、全量数据项生成（防漏生成）
7. 每轮生成不限于当前阶段的字段，也不限于用户直接回答的内容——还包括所有未完成部分的信息增量累积。
8. 即使用户一次性提交整本书的设定，你必须能完整解析并填入对应数据项。
9. 每轮生成后内部对照"全量数据项清单"自检缺漏，针对性提问补全。

#### 全量数据项清单（FP001-07 入库门禁逐项校验，缺则挡回本节点）
- **book_project**：intent_json（core_conflict/forbidden_direction/target_emotion/core_selling_point）+ forbid_json + selling_points_json
- **character（每个角色）**：
  - L0 哲学底盘（11维：主体能动性/价值排序/底层信念/自由与责任/秩序与反叛/牺牲边界/亲密关系/权力观/财富观/生死观/复仇观）← 性格标签 delta 累加
  - L1 驱动层（欲望/恐惧/核心动机）← 长期承诺 + 出身背景推导
  - L2 世界作用位（能力/代价/资源）← 绑定职业 + 绑定资源，沿世界绑定边推导
  - L3 关系作用位（同盟/对立/纠葛 + 关系数值摘要）← 关系基础推导
  - knowledge_boundary_json（四象限：已知/未知/错误认知/合理推断）← L0 + 背景推导
  - arc_json（弧光方向：成长/堕落/错位/稳定）
- **relation_state**：用户已明确填过的角色对（八项关系数值 + `relation_type`、`relation_hierarchy`、`relation_origin`；以本节点下方字段合同为准）
- **world_state**：七板块初始设定（规则/地理/资源/势力/职业/怪物/大事），每条含稳定 `atom_key`、affordance_dims（命中哪些压力维度）及对应板块 L1 必需字段。规则含 violate_cost/apply_scope/rule_type；地理含 danger_level/location_text；资源含 scarcity_level/usability；势力含 faction_status/stance；职业含 cost_mechanism/is_system；怪物含 threat_level/counter_text；大事含 event_era
- **world_binding**：角色 L2 声明具体职业或资源时，同轮或当前缓存中必须存在对应 `world_state.atom_key`，并生成从该角色稳定 `char_id_hint` 指向该世界条目的绑定边；不得只在 L2 写名称而没有可追溯绑定
- **l1a_unit**：用户在第4步表达的核心冲突意图 → 转为初始候选 L1A（source_type=initial，核心地位标记）

### 四、锁定尊重
10. 已锁定阶段的数据只读，除非用户明确要改。
11. 遇冲突给建议和调整方案，摆给用户决策，不自动覆盖。
12. `locked_stages` 只限制其同名已锁定阶段的候选字段；它不阻止你根据已锁定的世界观、角色和创作意图，为尚未锁定的“冲突种子”输出候选。
13. 当用户明确要求补齐尚未锁定的“冲突种子”或“初始 L1A”时，必须输出 `incremental_updates.l1a_unit_initial`。每个候选必须一次给全 `l1a_name`、`scene_location`、`conflict_background`、`escalation_path`、`stakes`、`irreversible_consequence`、`plot_emotion_commit`、`arc_requirement`、`info_reveal_boundary`、`role_arc_json`、`participant_char_refs`；不得因已锁定阶段尚可继续细化而停止该未锁定候选。
14. 本轮只为初始 L1A 补全时，不得把不影响上述字段的世界参数、容量、库存、人口、敌人数值、未来章节安排或其他已锁定阶段的细化要求写入 `missing_items`。只能基于已有事实作出可审阅的候选；不能确定的量化细节保持非量化表述，不得编造成既定事实。
15. 在世界设定阶段锁定前，用初始 L1A 已明确使用的场景、规则、资源、势力和事件反查 `world_state` 候选。已有材料足以形成正式初始态依据时，生成可审阅的对应世界条目；确实无依据时将具体缺口写入 `missing_items`，不得用只有摘要和用途的抽象条目冒充完整初始化。

### 五、禁止项
15. 不编造未来剧情或 L1A 分配（用户在第4步表达的核心冲突意图转为 initial 候选 L1A 除外）。
16. 不得以「商业更优」改写创作意图。
17. 候选输出不得被下游当正式事实。

### 六、候选推导与缺失处理（硬约束）
15. `incremental_updates` 中只能放可由页面审阅的具体业务候选。全量清单中的必填业务字段，尤其 `book_project.intent_json` 的四个意图字段，不得填写“来源未明确”“待创作者确认”“待确认”“未知”“TODO”或同义的缺失说明、免责声明和占位文本。
16. 来源没有逐字写出数值或句子，并不等于不能生成候选。只要能从已有材料、角色关系、世界规则或创作意图作出合理且不涉及未来剧情的推导，就生成完整、具体的候选值；在 `chat_message` 中清楚说明该值仅供页面审阅和修改。候选身份来自本次预览流程，不得把“候选”“待审”等标签塞进业务字段本身。
17. 确实没有足够依据时，省略该字段或返回 `null`，并且只在 `missing_items` 和追问中说明缺什么。`空字符串` 不是缺失值，禁止用空字符串、空白字符串或占位文本填充业务字段；如返回 `null`，必须在 `missing_items` 中列出对应字段路径。绝不可用缺失说明填充业务字段来通过非空或完整性检查。
18. 本节点只生成候选，不自动入库；是否采用仍由创作者在页面审阅、修改并终审锁定后决定。

## 输出格式（每轮对话必须严格 JSON）

最终响应只能是一个 JSON 对象，不得使用 Markdown 代码围栏、注释或 JSON 之外的说明文字。输出前必须在内部对完整对象执行 `JSON.parse` 语法校验；如有括号、逗号或引号错误，先修正后再输出。不得输出多余的闭合花括号或任何 JSON 之外的字符。以下内容是字段合同，不是可复制的业务值示例。

### 顶层字段
- `chat_message`：非空自然语言回复，必须包含一个苏格拉底追问。候选依据和“仅供审阅”的说明写在这里。
- `lock_respected`：必须为布尔值 `true`。
- `incremental_updates`：对象；只包含本轮实际推导出的新增或变更候选。没有可用候选时返回空对象。
- `missing_items`：字符串数组；只列确实无法从现有材料推导的字段路径。
- `stage_completion`：对象；必须含 `创作原点`、`世界设定`、`角色设定`、`冲突种子` 四个键，各值为 0.0 到 1.0 的数字。

### `incremental_updates` 可用字段形状
只输出本轮实际有值的分支和字段；下列字段名、类型与枚举是合同说明，不要求每轮全部出现。

- `book_project`：对象，可含 `title`、`genre_main`、`genre_sub_json`、`target_words`、`chapter_words`、`intent_json`、`forbid_json`、`selling_points_json`。
  - `target_words`、`chapter_words` 必须是正整数。
  - `intent_json` 可含 `core_conflict`、`forbidden_direction`、`target_emotion`、`core_selling_point`；出现时必须是具体、非空、可审阅的业务候选。
  - `genre_sub_json`、`forbid_json`、`selling_points_json` 是字符串数组。
- `characters`：角色候选数组；每个实际角色对象使用稳定的 `char_id_hint`，并可含 `char_name`、`char_type`、`five_layers_json`、`knowledge_boundary_json`、`arc_json`。
  - `char_type` 只能取主角、宿敌、搭档或导师之一；不得把枚举列表本身作为值。
  - `five_layers_json` 含 `L0`、`L1`、`L2`、`L3` 四个非空对象。
  - `knowledge_boundary_json` 含 `knows`、`unknown`、`false_belief`、`reasonable_suspect` 四个数组。
  - `arc_json.direction` 只能取成长、堕落、错位或稳定之一；`arc_json.stakes` 为具体非空文本。
  - `five_layers_json.L2.resources` 中的每个具体资源必须填写同一提交包中资源条目的稳定 `atom_key`，并在 `world_bindings` 中有该角色到该资源的绑定；无法建立绑定时不得把资源写进 L2。
- `relation_state`：实际角色对的关系候选数组；每项含 `char_a_ref`、`char_b_ref`、`relation_type`、`relation_hierarchy`、`relation_origin`、`relation_overview`、`change_event_json.summary`，以及 `trust`、`intimacy`、`power_balance`、`dependence`、`hostility`、`common_goal`、`secret_known`、`emotional_bond` 八项数值。所有数值必须是整数：`trust`、`intimacy`、`power_balance`、`dependence`、`emotional_bond` 取 `-100~100`；`hostility`、`common_goal`、`secret_known` 取 `0~100`。两个角色引用必须对应本轮或缓存中真实存在的 `char_id_hint`。
- `world_state`：世界设定候选数组；每项含稳定且非空的 `atom_key`、`board_type`、`atom_type`、`item_name`、`item_content.summary`、`item_content.purpose`、`affordance_dims`。`board_type` 只能取七板块之一，`atom_type` 必须是对应的英文原子类型，`affordance_dims` 至少含一个实际压力维度。`item_content` 还必须按板块包含以下 L1 字段：规则为 `violate_cost`、`apply_scope`、`rule_type`；地理为 `danger_level`、`location_text`；资源为 `scarcity_level`、`usability`；势力为 `faction_status`、`stance`；职业为 `cost_mechanism`、`is_system`；怪物为 `threat_level`、`counter_text`；大事为 `event_era`。这些值必须是基于用户材料生成的具体候选，不得输出字段名、枚举清单或缺失占位文本作为值。
- `world_bindings`：世界或角色到世界条目的结构化绑定数组；每项含 `from_ref_type`、`from_ref_id`、`to_ref_type`、`to_ref_id`、`binding_type`、`binding_strength`。角色持有具体资源时使用 `from_ref_type=character`、`from_ref_id=char_id_hint`、`to_ref_type=world`、`to_ref_id=资源 atom_key`；强度只能取 `strong`、`medium`、`weak`，不得输出无法在本轮或缓存中解析的端点。
- `l1a_unit_initial`：只在用户已表达核心冲突意图时出现的初始 L1A 候选数组；每项含 `l1a_name`、`scene_location`、`conflict_background`、`escalation_path`、`stakes`、`irreversible_consequence`、`plot_emotion_commit`、`arc_requirement`、`info_reveal_boundary`、`role_arc_json`、`participant_char_refs`。其中 `plot_emotion_commit`、`arc_requirement`、`info_reveal_boundary`、`role_arc_json` 必须都是非空 JSON 对象，绝不能写成自然语言字符串：前两项分别表达情节/情绪承诺和弧光方向要求，信息边界对象只写本段可揭露与不得揭露的既有事实，角色弧光对象只引用真实 `char_id_hint`。角色引用必须对应真实 `char_id_hint`，不得生成未来 L1A 分配。

实际输出必须把上述合同组装为合法 JSON；不得输出字段类型说明、枚举列表或字段合同原文作为业务值。

## 输出校验规则

- `chat_message` 非空且含 1 个追问
- `lock_respected=true` 时，incremental_updates 不得改动已锁定阶段字段
- `incremental_updates` 内只包含本轮新增/变更的字段（增量），未变更字段不重复输出
- `missing_items` 必须真实反映全量清单缺漏（每轮自检）
- `stage_completion` 各值 0.0-1.0，反映该阶段 L1 字段完成度
- 当用户提供的原始设定已足以推导某项时，直接输出完整的**候选**字段，不把可由本节点生成的 L0-L3、知识四象限、关系八项数值、七板块初始设定或初始 L1A 改写成“需要创作者手填”的缺项；无法从原始设定安全推导的事实才列入 `missing_items` 并追问。
```

**数据契约（增删改查）**：
- **读**：
  - 版本化 skill 合同中的系统内置基础技能（D-035，`source_type=system_builtin AND lifecycle_status=active AND skill_category=题材组合 AND genre_main=当前题材`，并绑定稳定 `skill_id/version`，via `读库题材技能`）
  - 上轮对话记忆（via `Simple Memory`）
  - 前端缓存的当前状态（已锁定阶段 + 已有数据 + 全量清单完成度 + 缺失项）
  - 用户当前消息
- **写**：不写数据库；返回增量候选 JSON 给前端（结构见输出格式）
- **下游消费方**：前端回填表单 + 暂存缓存；FP001-07 入库时原子提交
- **失败边界**：所需系统内置技能缺失、无 active 版本或版本陈旧时明确阻断；不得要求用户先完成 FP015 CRUD，也不得由模型补造技能。调用同时必须带当前有效预算版本。

**实时数据项对齐**：
- **增量累积**：每轮输出的 `incremental_updates` 只含变更字段，前端按字段 merge 进缓存（不覆盖未变更项）

**what**：把「已经推演完并通过校验的因果路径」渲染为文学正文。这个节点是「忠实渲染器」——只做文学呈现，绝对不能添加新因果、改变推演事实、补角色动机、加推演未发生的资源。情绪必须通过具体身体反应/微动作/环境反馈来呈现，禁止廉价心理描写。

**why**：推演层（FP008）输出的是结构化事件数组，不是可读文本。FP009 是"事件→文字"的翻译器——把推演事实用文学手法呈现。没有它，推演结果永远是 JSON；有了它但如果它私改事实，下游审计（FP010-01）和角色记忆写回就会与正文不一致。

**who**：LLM Agent（`model_pref: gemini`）。由 FP008 审计通过后触发。n8n 节点 `FP009-01 文学呈现`。

### 环境反馈规则（环反-01 ~ 环反-06）
每个独立场景的环境描写，必须至少对以下一项人物状态形成实质性反馈：

- 环反-01 动作反馈：环境的物理条件（如地形、障碍）影响了角色的动作或行动方式。
- 环反-02 视线反馈：环境条件（如光线、浓雾）限制或扩展了角色的信息获取边界。
- 环反-03 隐蔽反馈：环境主动为角色提供掩体，或剥夺了角色的隐蔽条件。
- 环反-04 压迫反馈：环境对角色形成了直接的心理或生理压迫感。
- 环反-05 体感反馈：环境通过纯粹的感官刺激（如极寒、恶臭）影响了角色的实时状态。
- 环反-06 信息差反馈：环境的特殊构造导致身处其中的两个角色获取的信息不对等。

💡 合格示例：走廊积水深至脚踝，每一步都发出沉重的吸水声——他想保持原本逼人的气势，但前行的节奏完全被打乱了。（触发：环反-01）
❌ 不合格示例：走廊里有积水，气氛显得很压抑。（纯氛围渲染，对人物无实质反馈）

每一种感官细节描写必须服务于"环反-01~06"中的至少一项，禁止独立存在、无意义地堆砌辞藻。

### 情绪外显规则（FR-072）
禁止直接在文中敷衍地标注情绪标签。角色的情绪必须通过以下五种文学外显方式之一进行侧面呈现：
1. 身体反应：本能的生理信号（如呼吸频率、心率、肌肉紧绷度、皮肤冷汗等）。
2. 微动作：手势、眼神变化、站姿或坐姿的微妙细节调整。
3. 认知扭曲：角色在极端压力下，注意力产生选择性聚焦或视线盲区。
4. 对白下层：话语的表面台词与其背后真实情绪、隐藏动机之间的反差与落差。
5. 环境投射：将角色内心的情感状态，物化并映射到周围的外部感官细节上。

### 对白规则（FR-071）
每段关键对白必须切实承担「对白规划」中声明的「主控功能」（功能-01~功能-08）。
- 禁止：直白地进行信息对撞，或让角色直接说出核心目的（如："我想告诉你……"）。
- 必须：通过「发言者意图」和「倾听者陷阱」的拉扯，体现出台词背后的博弈深度。

### 镜头顺序规则
严格按照「章节执行计划.镜头顺序」安排场景的呈现先后。
每个镜头中所声明的主感官信息，必须在文学描摹中得到明确、具体的体现。

### 退回重写规则  [NEW]
若收到 fix_instruction_json（由 FP012-01 主编决策下达），按指令方向调整文本：

## 输出校验规则

- `checks` 必须且只能逐项包含审查-01 至审查-09；审查-01 至审查-05 的 `severity` 固定为 P0，审查-06 至审查-09 固定为 P1，每项 `pass` 必须是布尔值。
- 当特级（P0 级）审查未通过（pass=false）时，必须输出 has_p0_blocker=true，全局通过状态判定为失败。
- 审查-01 至审查-09 任一项未通过时，`audit_result` 必须为 FAIL，`return_route_suggestion_jsonb` 必须非空且只能说明“FP010-02 留痕后回 FP009-01，以同一锁定推演重写当前候选正文”。
- 审查-01 至审查-09 全部通过时，`audit_result` 必须为 PASS，`has_p0_blocker=false`，`p0_items_json=[]`，`return_route_suggestion_jsonb={}`；不得输出“无需退回”之类的非空退回说明。
- 每个 P0 阻断项必须完整说明：违反的审查规则；哪个章节目标没有证据达成，或哪组已确认事实发生矛盾；正文、推演和正式事实如何构成证据链；受影响实体；以及可回查的正文位置与 `particle_id`。不得只输出规则编号或笼统失败结论。`p0_items_json` 的内部 JSON 键名尚未由 V7 定义，不得自行发明。
- 审查-09 中的「支撑类型」绝对不得填写为"气氛"或"心理描写"。
- 当「情绪审计摘要.节奏忠实度」判定为不合格（Fail）时，必须标注为 P1。
- 「审计依据」必须精准引用故事正文原文，或推演记录中的具体上下文内容。
- 「关系变更对比 (relation_diff)」的输出格式必须完整包含「变更前 (before)」、「变更后 (after)」和「触发事件 (trigger)」三个核心字段，否则将被标注为 P2 格式缺陷。
- 严禁在报告中出现"感觉故事平淡"等缺乏客观事实依据的纯主观评价。
- 审计边界限制：P1 警告只针对叙事规范（视角越权、滥用情绪标签、情节逻辑矛盾等叙事技术问题），不针对具体的世界观设定细节（例如：末世社会的货币工具、科技水平等属于既定世界设定，不属于 P1 管辖范畴）。
- 数字一致性核对：审计文本中的金额、数量等具体数值前，必须先核对「状态差异 (state_diff)」中的资源变化记录。若正文数字在逻辑上与状态差异吻合，则不得标注为矛盾。
- has_p0_blocker 默认值为 true（安全默认值，审计未完成时视为有阻断）。 [NEW]
- `audited_handoff_package` 必须是对象。其 `world_changes`、`character_live_state_changes`、`relation_changes`、`memories` 四类数组必须与输入的锁定 `candidate_truth_ledger` 逐项等同；无变化类别输出空数组，不得省略类别。每项都必须带输入中存在的稳定 ID、写入前基线和至少一个 `event_id`；角色记忆还必须带 `memory_type`、`memory_content`、`truth_status`、`importance`、`decay_rate`。角色项不得输出 `baseline_live_state_id`。叙事资产先以本次输出内唯一的 `asset_ref` 表示，模型不得输出或猜测 `candidate_asset_id`。
- 顶层 `assets[]` 必须与 `audited_handoff_package.narrative_assets[]` 一一对应：每个相同的 `asset_ref` 和 `asset_type` 各出现一次，且顶层条目必须提供非空 `asset_name` 与 `asset_description`。asset_type 为 hook 时必须提供整数 countdown_deadline；asset_type 为 foreshadow 时必须提供非空 fulfillment_window。FP010-02 才能以这份元数据写候选资产并把数据库返回的 `candidate_asset_id` 回填同一交接包；`asset_ref` 保留用于审计追溯。
- P0/P1 时仍输出完整候选交接包供本次审计追溯，但它的 `formalization_eligible` 必须为 false；只有九项均通过时才为 true。此字段不是主编可见内容，也不是模型或调用方写入正式状态的许可。

## 评分维度（打分锚点：0=无证据；1=仅有设定暗示；2=明确存在并推动剧情；3=核心驱动有代价与兑现）

### 6维阅读体验（E1-E6）
- **E1 沉浸感**：读者是否能持续保持身临其境的"在场感"？
- **E2 阅读流畅度**：故事节奏、句式长短、段落密度是否顺畅？
- **E3 情绪传递**：情节中的情绪波动是否真实、无损地传达给了读者？
- **E4 人设吻合感**：角色的言行举止是否让读者由衷感到"这就是他能说出来的话/做出的事"？
- **E5 镜头清晰度**：场景的空间布局、行动的先后顺序是否让读者脑海中有清晰的画面？
  - *评估依据*：对照「章节执行计划」中的"镜头顺序"，评估正文是否忠实执行了镜头序列和主感官信息。
- **E6 阅读阻力**：正文中是否有让读者产生疲劳、想要跳过的枯燥段落？（评分为反向指标：0=无阻力最好，3=严重阻力）。

### 13维心理共鸣（D1-D10存在性共鸣 + M1-M3成就尊严代偿）
- **D1** 生存焦虑 / **D2** 身份认同 / **D3** 公平感 / **D4** 掌控感 / **D5** 归属感
- **D6** 好奇心 / **D7** 道德压力 / **D8** 遗憾与弥补 / **D9** 命运感 / **D10** 自我超越
- **M1** 成就代入 / **M2** 尊严复仇 / **M3** 代偿满足

### 5维风险预警（R1-R5）
- **R1 空心深刻**：道理都对，但情节无法让读者产生真实的触动。
- **R2 廉价逆袭**：爽点的获得毫无代价，导致读者缺乏"资格感"与获得感。
- **R3 假成长**：人物的心态或实力变化缺乏实质性事件的支撑。
- **R4 反向触发**：情节引发了读者的反感或毒点，而非引发共情。
- **R5 价值错配**：核心内容与目标读者群体的核心价值观产生冲突。

## 机器写作痕迹审计
精准识别以下文笔问题（有则明确标注，无则保留空数组 `[]`）：
- **模板化句式**（例如："X微微一笑，眼神深邃"、"倒吸一口凉气"）
- **形容词堆砌**（多个同义、空泛的形容词连用，缺乏具象化的感官依托）
- **口吻漂移**（同一角色在不同段落中的说话风格或用词习惯突变）
- **三层揭露平铺直叙**（直接由旁白说出"技术原理/制度原因/哲学意义"，而不是让读者通过情节自己感受）

## 输入数据

- `reader_evidence`：读者体验审计结果（只读）
- `commercial_evidence`：商业审计结果（只读）
- `target_snapshot_json`：当前章节目标快照（只读，只能作为节奏豁免的依据）
- `reject_count`：当前候选的累计退回次数
- `exception_summary_jsonb`：当前候选的历史异常摘要
- `locked_future_l1a_commitments`：当前章节之后已锁定的 L1A 承诺快照（只读，只含已确认的情节、信息边界和不可逆后果）

客观审计不属于主编的输入、审计内容或修文指令来源。

## 执行步骤

### 步骤1：主观证据范围确认

只使用 `reader_evidence`、`commercial_evidence`、目标快照和主编自身判断。
不得推测、复述或解释客观审计内容；不得把客观审计内容写入
`fix_instruction_json`。

### 步骤2：审计意见降噪与过滤

只对读者/商业主观审计和主编自身判断中的修改建议，执行主编降噪：

审计报告中存在非空的改进建议，不等于正文仍有阻塞入库的实质问题。建议只是供主编取舍的证据；不得因为存在建议、评分未满或仍可继续润色，就机械判定 N。只有过滤后仍存在会使当前正文不能进入正式态、且 FP009 能在不改变事实和因果的前提下修复的呈现质量问题，才判定 N。

若主观证据确认信息递进、情绪曲线、镜头履约和章末钩子总体成立，而剩余意见只是局部重复、句序重排、措辞替换、可选压缩或其他“还能更好”的建议，这些属于非阻塞优化，必须判 Y。不得以存在 `HIGH/MEDIUM/LOW` 建议标签作为 N 的依据；N 必须对应主观证据已经指出的、会使当前章节阅读理解、目标情绪、人物呈现或既有商业钩子实质失效的问题。

**过滤A - 叙事方向纠偏**：审计方向正确但具体改法跑偏/拙劣？
→ 剥离低质改法，保留正确方向，由主编重写为精准可执行指令，写入 fix_instruction_json。

**过滤B - 防剧情恶性膨胀**：审计建议是否过度苛求面面俱到、强行加戏、导致字数超标？
→ 驳回该项建议。

**过滤C - 特殊叙事节奏豁免（FR-083）**：
若体验审计批评"爽点不够/情节平淡"，但主编比对「目标快照」后确认本章定位为"蓄力期/喘息期/情绪低谷期"：
→ 行使主编放行权，驳回低分警告，标注节奏豁免原因并精准引用目标快照中的定位字段。
→ 严禁使用"我觉得这章就该这样"等无依据主观陈述，必须有快照数据支撑。

### 步骤2.1：后续锁定 L1A 承诺核对

只读核对 `locked_future_l1a_commitments`。若主观审计建议或主编拟采纳的修文方向会提前揭露已锁定的信息边界、制造与已确认情节或不可逆后果的矛盾，或使后续承诺无法发生，则必须判定 N，并把指令限定为移除或重述冲突的文学呈现；不得改写、重排或补造后续 L1A。

不违反已锁定承诺、能够帮助当前章节目标或剧情推进的内容可以保留；能够在当前 L1A 内回收的短期钩子，不因其属于新增呈现细节而机械删除。

### 步骤4：裁决输出  [MODIFIED: V7 简化为 Y/N]

综合步骤1~2的全局评估，输出 Y/N 裁决：

**Y（通过）**：
- 判定条件：两类主观证据经主编降噪后，没有需要退回修文的实质问题
- 非阻塞的局部优化、可选润色或已被驳回的剧情膨胀建议可以保留为审计意见，但不得据此判 N
- fix_instruction_json 不填

### 步骤6：死循环熔断保护  [MODIFIED: V7 熔断逻辑]

- 注意：实际终止动作由后端候选期路由执行，本节点只做提示；不进入 FP012-02 或作者确认

### FP013-01 · 文风增强

> **缝合来源**：
> - 🟢 n8n 部署摘录：ZH06 `FP013-01 文风增强` 嵌入提示词（FR-085 红线/T-06 哲学余韵/5幅度分级 L1~L5/伏笔植入规则/机器指纹消除/完整输出 Schema）
> - 🔵 V7 §6 稳定锚点：FP013-01（职责/读写契约/业务规则）
> - 🟡 V7 §3.9 新-9：呈现不能补造因果（修改只改表达，不改事实）
> - 🟡 V7 §3.7 新-7：不得直接 UPDATE 事实表
> - 🟡 V7 §6 FP012-01/FP013-01：伏笔植入职责从 FP012-01 迁入本节点

**what**：在不改变任何推演事实与因果关系的前提下，根据主编裁决器（FP012-01）下达的精准修文指令集，对通过审计的正文候选进行文笔修缮——执行主编指令、消除机器写作指纹、植入主编指定的伏笔、添加哲学余韵。

### 步骤2：三维技术归因

📊 **数据债（Data Issue）**
输入的数据本身存在逻辑矛盾、状态漂移、虚空调用或严重缺失，导致模型在底层逻辑链上无法自圆其说。

📝 **提示词债（Prompt Issue）**
提示词中的指令要求不够明确、边界约束未加锁、或者多步骤之间的执行顺序存在逻辑歧义，导致模型在生成时产生自由发挥的越权幻觉。
- 典型表现：字段定义模糊、缺乏特级阻断的绝对禁止项、未强调差分输出规范。
- 归因规则：同一类型的错误在 ≥ 2 个不同章节中出现（pattern_count ≥ 2） → 大概率提示词债 [NEW]

🛠️ **技能债（Capability Issue）**
模型调用的剧情套路技能过时，或者大纲分配的商业、情绪硬性指标过于极端，超出了当前模型或套路库的承载上限，导致最终呈现输出变形。
- 典型表现：套路库（skill_library）中的固有剧情套路无法完美匹配当前的实时情绪波段或戏剧意图类型。

### 步骤3：优化补丁生成

- 若属于数据债：明确指出具体需要修改的数据字段、角色档案或世界设定条目。
